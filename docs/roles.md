# 分级管理员与职责分离（F26）

一个超级管理员什么都能干、出了事也查不清是谁干的——这是等保测评
最先查的毛病。AgentGate 把管理权拆成五档，照等保三级「三权分立」
的思路：管系统的人不能改安全策略，管安全的人不能碰审计，审计的
人只能看不能动；再加一个只跑运维的角色。模型借鉴 IP-guard 的分级
管理员体系与 GB/T 22239-2019 三级要求的系统管理员 / 安全管理员 /
审计管理员三分法（另见 [docs/oidc-sso.md](docs/oidc-sso.md) 的角色映射）。

## 角色

| 角色 | 身份 | 能干什么 | 不能干什么 |
|---|---|---|---|
| `admin` 平台管理员 | 系统管理员 | 全部权限；**唯一可以分配角色的角色** | 不能改自己的角色、不能禁用自己 |
| `security` 安全管理员 | 安全管理员 | 与 admin 同等的策略管理权：改分级策略、批例外、导审计、管渠道与令牌 | **不可分配角色**（避免自我提权） |
| `auditor` 审计员 | 审计管理员 | 只读审计与报表：查审计、验链、导审计、生成与导出合规报表、看统计 | 不可改任何策略与配置，不可看令牌 |
| `operator` 运维员 | 运维管理员 | 渠道增删改与密钥管理、令牌限流、缓存开关与清空、OTel 状态与测试 | **不可看审计**（审计、统计、报表、证明记录全部 403） |
| `employee` 员工 | 普通员工 | 使用 Agent 能力、申请例外、起草技能 / 模板 / 知识包 | 无管理面 |

权限的唯一事实来源是 `internal/roles` 的矩阵（`roles.Can`），管理
台导航只按同一矩阵隐藏入口，服务端每个端点都按矩阵守卫——藏菜单
不等于授权，真正拦人的是 API 层的 403。

## 关键操作：对应角色 + 全程留痕

- **改分级策略**（渠道信任类型与密级上限、证明策略、例外审批、知识
  库与模板的审核发布、预算、告警 Webhook、组织同步、安装包分发）：
  仅 `admin` / `security`。
- **批例外**（批准 / 驳回 / 撤销高密级调用例外）：仅 `admin` /
  `security`；批准本身记审计，凭证原文只返回一次。
- **导审计**（审计 NDJSON 导出、报表 CSV 导出）：`admin` /
  `security` / `auditor`；导出动作本身记 `audit_exported` 审计事件。
- **归档审计**（把事件移出热日志）：仅 `admin` / `security`——
  这是破坏性操作，审计员只能读不能动。
- 每次角色变更记 `user_updated` 审计事件（操作者、目标用户、角色
  变更前后、是否禁用），不含任何敏感内容。

## 用户管理

管理台「用户与角色」页（`admin` / `security` 可见列表；改角色与
禁用仅 `admin`）：

- `GET /api/users`（admin/security）：用户列表（用户名、姓名、部门、
  角色、角色来源、账号来源、是否禁用），**永不返回密码哈希**。
- `GET /api/users/roles`（admin/security）：角色分工说明卡片（与本文档同款）。
- `PATCH /api/users/{id}`（仅 admin）：改角色 / 部门 / 是否禁用。
  护栏（违反返回 400）：
  - 不能改自己的角色、不能禁用自己；
  - 不能动最后一位启用的平台管理员（降级或禁用都会被拒绝）；
  - 角色必须是已知角色（`admin` / `security` / `auditor` /
    `operator` / `employee`）。
  - 改角色后账号的角色来源记为 `local`——此后 OIDC 登录不再覆盖
    它（见下）。
  - 禁用账号会立即吊销其全部网页会话（`auth.RevokeUserSessions`）。

用户没有独立的新建接口：账号来自演示种子、OIDC 即时开户（F9）与
组织同步建号（F21），角色一律在上述入口分配。

## OIDC 组映射

IdP 只认身份、不认权限——这是 F9 定下的红线，F26 没有推翻它，只
是在管理员**显式配置**的前提下开了一个受控的映射口子：

```bash
AGENTGATE_OIDC_GROUPS_CLAIM=groups              # 组取自哪个 claim，默认 groups
AGENTGATE_OIDC_ROLE_MAP=auditors:auditor,ops:operator
```

- 映射只认 `auditor` / `operator` / `employee` 三档；`admin` 与
  `security` 写进映射会被启动校验拒绝（OIDC 因此不启用，本地
  登录继续可用），`internal/auth` 层还会再挡一次——即使映射函数
  被错配成返回 admin，JIT 开户也不会提权。
- 组 claim 取自 ID token 或 userinfo（两者合并取并集），可以是字符
  串数组、单个字符串亦可；claim 名可配（有的 IdP 叫 `teams`）。
- 映射只作用于 IdP 管理的账号（角色来源为 `oidc`，含 F26 之前已
  开户、角色来源为空的旧 OIDC 账号）：每次登录按当前组成员关系重
  新定角色——进了映射组得对应角色，退了组回到 employee。
- 管理员在控制台改过角色的账号即转为本地管理（`role_source:
  local`），此后 IdP 映射不再覆盖它——本地决定优先于 IdP。
- 未配置映射时 OIDC 登录永远不碰角色（F9 行为不变）。
- `GET /api/auth/oidc/status`（admin/security）返回映射表（组名与
  角色是管理配置、不是密钥，可以展示）。

演示模式新增两个账号（`internal/seed`，密码均为 `demo12345`）：

- `auditor` / 审计员（审计部）：登录后只能看到总览、用量统计、审计

  得到 403。

## 已知限制

- 角色是粗粒度的五档，没有按部门或按资源的细粒度授权（如「只能
  管研发部的渠道」）；部门级授权留待后续轮次评估。
- OIDC 映射是登录时同步：组关系变化在用户下次登录时才生效，不会
  主动吊销已发出的会话；离职禁用仍走组织同步（F21）或管理员手动禁用。
- `security` 保留与 `admin` 同等的策略权是 F26 之前既有行为的延续
  （此前 `requireAdmin` 即 admin | security），本轮没有降级它；
  若将来要收紧，应把 `security` 的权限再拆一档。
