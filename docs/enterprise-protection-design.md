# 企业级防护方案设计

> 项目定位：不绑定任何单一桌面 Agent 的企业 Agent 平台（Go 实现，后续开源）
> 员工可随意使用 DSH、WorkBuddy 等通用桌面 Agent 接入企业能力；企业的系统、知识、模型、权限与审计沉淀在平台侧。
> 本文调研对象：New API（QuantumNous）及其生态、LiteLLM Enterprise、Cloudflare AI Gateway、阿里云 AI 网关、华为云 WAF 大模型检测、WorkBuddy 企业版安全白皮书（腾讯，2026-10-30）。
> 日期：2026-11-21

---

## 1. 先说结论

各家的企业级防护，拆开看其实是同一套分层防御，只是覆盖范围不同：

| 厂商/项目 | 覆盖范围 | 最值得借鉴的点 |
|---|---|---|
| New API（开源网关） | 模型 API 流量 | 令牌权限+模型访问控制+调用审计；请求策略（文本过滤）；安全与限制（限流、SSRF 防护、令牌数量上限）；敏感配置读取不回显 |
| New API 最新版 rc.50 | 模型 API 流量 | 请求处理插件管线：请求过滤、请求脱敏、内容审核，可按全局/分组/渠道/模型生效，支持试运行，每处修改记入日志 |
| AstrLink（New API 作者的本地隐私网关） | 员工本机 | 敏感信息在离开本机前检测：规则+本地小模型（AstrLink Guard，int8 不到 40M，CPU 可跑，识别个人信息/凭据/IP/网址），策略为提醒/拦截/可逆脱敏（占位符），响应在本地还原，映射表不出本机 |
| 幻城网安版 New API（安全网关二开） | 模型 API 流量 | VGuard：强/弱词分级封禁 + 审核模型同步/异步复审，违规事件可按用户检索全链、解封；日志合规归档（热存 7 天、违规 30 天，zstd 压缩 NDJSON 归档 180 天）；渠道健康分智能路由 |
| LiteLLM Enterprise | 模型 API 流量 | 企业版清单：SSO/SCIM（OIDC/SAML）、JWT 鉴权、审计日志+保留策略、组织/团队 RBAC、IP CIDR 白名单、虚拟密钥轮换、密钥托管（Vault/KMS）、按 key/team 的 Guardrails（Presidio PII 脱敏、Lakera 提示词注入）、按团队关日志（GDPR）、日志导出对象存储 |
| Cloudflare AI Gateway | 模型 API 流量（托管） | DLP：实时扫描 prompt 与 response 中的 PII/金融/医疗/自定义模式，动作 flag/block，全提供商统一策略；Guardrails 双向内容审核。短板：托管形态，流量过第三方网络，不适合数据主权/离线场景；流式 DLP 需缓冲全响应，首 token 延迟上升 |
| 阿里云 AI 网关 | 模型 + MCP + Agent 流量 | 三层安全：网络（WAF、IP 黑白名单）、数据（消费者鉴权、后端密钥 KMS 托管不落盘）、内容（AI 安全护栏实时拦截 + 转发前数据脱敏插件）；MCP 工具级细粒度授权（按调用方身份、按单个工具）；按消费者观测/限流/计量 |
| 华为云 WAF 大模型检测 | 模型 API 流量 | 输入侧提示词注入检测+合规检测，输出侧响应合规检测，动作可设为仅记录/脱敏/拦截 |
| WorkBuddy 企业版（腾讯安全白皮书） | 桌面 Agent 本机 + 生态 | 控制前置：外部能力加载前风险检测、高危命令执行前确认、一键叫停；原生沙箱（文件读写/命令收敛在授权目录，敏感路径默认保护 106 条规则，高危命令前置询问）；文件改动每轮自动备份、删除进回收站、可整体回滚；敏感信息在输入框/工具返回/数据外发三个入口本地识别脱敏、全链路加密、推理侧可选可信计算（明文不出域）；技能/专家全生命周期安全检测（上架前风险文件+沙箱行为检测、实名核验、能力评测，上架后持续动态检测）；联合终端安全管控影子 AI 应用 |

**对我们的启示：**
- New API 一系解决的是"模型流量怎么管"，不管 Agent 本机、不管加密文件、不管能力/MCP 治理。
- WorkBuddy 企业版解决的是"自家 Agent 怎么管"，绑自家客户端和腾讯生态，闭源，企业只能信任厂商。
- **我们的空间：开源、中立、自托管，把防护从网关延伸到端侧 + 能力侧，且不绑任何 Agent。**

## 2. 核心难题：加密文件 + Agent

企业透明加密（绿盾、天锐等）的原理：文件落盘为密文，白名单进程打开时才给明文。

- 给 Agent 开进程白名单 = 给它开一个合法明文出口。真正的风险不在"读"，在"读完往哪送"。
- 因此白名单必须三件套：**进程白名单 + 网络出口白名单 + 模型白名单**。
- 闭源云端 Agent 过不了审的原因不是"会偷数据"，而是闭源、云端计量、自动更新，企业无法验证其行为，安全部门无法为核心密级文件签字。
- 开源 Agent（如 DSH）也不是天然安全：连公网模型 API 一样带出数据。它能进白名单的理由是**可控**：可审计、可锁定版本/自编译签名、可锁配置、可断网。

### 解法：数据分级路由（本设计的核心创意）

不做一刀切的允许/禁止，而是网关在转发前识别数据密级，按密级决定去向：

公开/内部走签约云模型（零留存/不训练承诺）；分级放行绑的是「通道信任类型」，不是「企业有没有自己的模型」——私有模型从必需项降为可选项之一。

| 数据密级 | 判定来源 | 允许的模型去向 |
|---|---|---|
| 公开 | 无敏感命中 | 任意已接入模型（含公网云模型） |
| 内部 | 一般内部关键词/文档标记 | 企业签约云模型（零留存协议） |
| 机密 | DLP 命中敏感类目、加密文件来源标记 | 默认：网关脱敏后上云（原文不出公司，云端只见代号、响应还原）；可选：厂商专有云 / VPC 部署 |
| 绝密 | 核心类目命中、绝密文件标记 | 本地小模型（单机可跑）处理简单任务，或直接拦截并明确提示「无合规通道」 |

这样即使受管 Agent 读到了明文，网关仍是最后一道闸：数据去哪一级模型，由策略决定，不由员工和 Agent 决定。

### 2.1 但网关只管得住"模型通道"——云盘等侧信道防不住（2026-11-21 补充）

以 WorkBuddy 这类自带云服务的 SaaS 型 Agent 为例，对它开白名单后还有一条网关完全看不见的通道：**它自带的网盘/云文档与跨端同步**。Agent 读到明文后，把文件或加工成果存进厂商网盘，员工在公司外用个人设备即可取回。整个过程不经过企业模型网关，流量只是到厂商域名的 TLS 连接，企业侧无法做内容检查。

这类 Agent 的外带通道至少包括：

1. 模型推理通道（唯一能被企业网关接管的通道，前提是它允许改模型地址）
2. 厂商网盘/云文档存储与分享
3. 跨端同步（PC / 手机 App / 小程序实时同步任务与产物）
4. IM 远程调度与结果回传（微信、企微等）
5. 遥测与日志上传

**关键判断：对这类 Agent，企业剩下的只有行为审计，而审计是事后追溯型控制，不是预防型控制。** 数据一旦进了厂商网盘，就脱离了企业的数据生命周期：留存多久、企业能否删除、员工离职后是否还能访问，都不受企业控制；审计日志最多告诉你"已经带出去了"，拦不下，也追不回。而且审计的前提还是厂商愿意提供完整日志——闭源产品给多少，企业只能用多少。

即使企业在终端再叠一层传统 DLP，也防不干净：Agent 可以改写、摘要、转码内容，语义化外带绕过文件指纹类检测；而它与厂商之间的 TLS 通道无法区分"正常模型调用"和"网盘上传"，不拦截其域名就拦不住上传，拦截则产品不可用。

**结论：能不能给一个 Agent 开加密白名单，不取决于它的厂商白皮书，而取决于它是否通过下面的准入标准。**

#### Agent 白名单准入标准（建议作为产品内置评估清单）

| # | 标准 | DSH（受管构建） | WorkBuddy（SaaS 版） |
|---|---|---|---|
| 1 | 无自有网盘/云同步，或可由企业策略彻底关闭 | ✅ 本地运行，无厂商网盘 | ❌ 网盘与跨端同步是核心功能 |
| 2 | 全部模型流量可改指企业网关 | ✅ 可配置 Base URL | ⚠️ 内置模型/积分体系不经企业网关 |
| 3 | 全部网络目的地可枚举、可审计 | ✅ 目的地由配置决定 | ❌ 账号、计量、同步、遥测多通道 |
| 4 | 无 IM 等远程调度通道，或可关闭 | ✅ 无 | ❌ 微信/企微远程调度为卖点 |
| 5 | 版本可锁定、更新可控，可自编译/签名分发 | ✅ 开源可自构建 | ❌ 厂商自动更新 |
| 6 | 本地数据目录可枚举，离职可由 MDM 彻底清除 | ✅ | ⚠️ 数据已同步至厂商云端，本地清除无效 |
| 7 | 代码/行为可审计，不依赖厂商单方承诺 | ✅ 开源 | ❌ 闭源，靠白皮书与认证 |

不通过准入的 Agent 不是不能用，而是**不进白名单、不碰加密文件**：在分级体系里归自带级，只处理非加密、低密级数据。这一条要写成产品的硬规则，而不是部署建议。

#### 对受管 Agent 的预防型控制：进程级出口守卫

对通过准入的受管 Agent，预防不靠审计，靠把出口物理收窄，随受管包下发：

- 操作系统防火墙规则按**进程**下发：受管 Agent 进程只允许连接企业网关与本地隐私网关（127.0.0.1），其余出站一律拒绝（Windows 防火墙出站规则 / macOS pf + Little Snitch 类策略 / Linux nftables cgroup）
- 受管 Agent 无网盘、无同步组件，工作产物只落本地工作目录或企业内网存储（由 MCP/工具通道写入，仍过审计）
- 审计在此定位为第二道防线：证明守卫规则未被篡改（定期上报规则与进程哈希，即第 1 层的 Agent 证明），而不是指望它拦下外带

一句话：**SaaS 型 Agent 的防护上限是"可审计"，受管 Agent 的防护下限是"可预防"。企业加密文件只能交给后者。**

## 3. 五层防护架构

### 第 0 层：端侧（员工本机）— 借鉴 AstrLink + WorkBuddy 沙箱

- **本地隐私网关（sidecar）**：以 `127.0.0.1` 本地代理形态运行，任何能改 Base URL 的桌面 Agent 都可接入（这是"不绑 Agent"在端侧的落点）。请求离开本机前完成：
  - 规则检测（正则 + Aho-Corasick 敏感词）+ 本地小模型检测（参考 AstrLink Guard：小体积、CPU 可跑、针对凭据/PII/IP/代码优化）
  - 策略处置：提醒 / 拦截 / 可逆脱敏（每个敏感值生成独立占位符，映射表只存本机，响应回程本地还原，保证 Agent 的工具调用照常工作）
  - 试运行（dry-run）模式：先只记录不拦截，统计误报后再切正式策略
- **受管 Agent 包**：企业分发的受管 Agent（如锁定配置的 DSH 构建）才有资格申请加密软件进程白名单：
  - 工作目录沙箱、敏感路径默认拒绝（如 `~/.ssh`、凭据目录）
  - 高危命令前置确认、一键叫停、文件改动自动备份与整轮回滚
  - 只允许连接企业网关地址，插件只允许安装审核过的清单
- **影子 AI 治理（远期）**：与企业已有终端安全软件联动，发现未登记的 AI 应用使用企业数据时告警（WorkBuddy 与腾讯 iOA 的做法）。

### 第 1 层：身份与设备

- SSO：OIDC / LDAP / AD，SCIM 组织同步（借鉴 LiteLLM Enterprise 清单）
- 设备登记 + Agent 证明（attestation）：登录时上报 Agent 类型、版本、二进制/配置哈希、插件清单，平台据此发放**分级令牌**
  - 受管级令牌：可访问敏感能力与机密数据通道
  - 自带级令牌（BYOA，如员工自装的 WorkBuddy）：只可访问通用能力，模型流量强制过网关 DLP
- 令牌短时有效、可吊销、数量上限；登录限流与账号级失败锁定（按账号而非仅 IP，防暴力破解且防锁死他人）；查看密钥等敏感操作需 step-up 二次验证
- 网关入口 IP CIDR 白名单

### 第 2 层：企业网关（核心）— 借鉴 New API 管线并扩展

Go 网关实现一条**请求处理管线**（插件化，可按部门/分组/模型/Agent 等级生效，每一步可独立开关、可试运行、每次改动记入审计日志）：

1. 鉴权（分级令牌校验）
2. 限流与配额（用户/部门/模型维度 RPM、TPM、月度 token 配额）
3. 请求过滤（敏感词 AC 自动机，命中拦截或替换掩码）
4. DLP 检测（服务端二次检测，与端侧形成双层：端侧漏检的网关兜底）
   - 类目：凭据/密钥、PII（身份证/手机/邮箱/银行卡）、企业自定义类目（项目代号、客户名、图纸编号等正则/词表）
   - 检测手段分级：规则（快、确定）→ 小模型/审核模型（慢、处理语义类，如提示词注入）
5. 提示词注入检测（规则 + 审核模型同步/异步双路，借鉴 VGuard）
6. **数据分级判定与路由**（见第 2 节表格）
7. 脱敏/令牌化（需要送云模型但含可脱敏字段时执行；映射存企业侧 Vault，与端侧脱敏二选一或叠加，见"待决策"）
8. 路由与容灾（渠道健康分：成功率衰减 + 首 token 延迟 + 在途负载，借鉴幻城智能路由；失败重试与切换）
9. 响应侧检测（输出合规 + 响应 DLP 扫描；注意流式响应做 DLP 需缓冲，会增加首 token 延迟，策略上默认只扫请求侧，响应侧仅对高密级部门开启）
10. 审计落盘（见第 4 层）

管理面安全（New API 的经验与教训）：
- 上游密钥、系统密钥**加密存储**（主密钥/KMS），绝不明文落库（New API 设置值明文存 DB 是已知短板，我们要避开）
- 敏感配置读取接口**不回显**（整项省略而非打码）
- SSRF 防护（上游地址、MCP 地址、回调地址白名单/私网拦截）、CORS 白名单、安全响应头（CSP/HSTS 等）由内置反代模板提供
- 渠道熔断、健康检查、优雅关闭

### 第 3 层：能力与 MCP 治理

- MCP 网关：工具级授权（按部门/角色/Agent 等级、按单个工具），不只是 Server 级（借鉴阿里云）
- 凭据服务端托管：ERP/CRM 等系统凭据加密存服务端，永不下发员工机；每次工具调用以员工身份鉴权并审计
- **工具返回也要过 DLP**：工具结果是敏感数据进入模型上下文的第二入口（WorkBuddy 的"三个入口"之一），返回内容在进模型前同样扫描/脱敏
- 技能/插件供应链安全（借鉴 WorkBuddy 生态检测 + dsh-ee 审核）：
  - 上架前：风险文件静态扫描 + 沙箱行为检测 + 依赖/许可证/密钥泄漏检查
  - 签名与版本锁定，企业 scope 不回落公共源（防依赖混淆）
  - 上架后持续复扫，新版本需重新审核，问题包一键下架并全员失效

### 第 4 层：审计与合规

- 全链路审计字段：谁、何时、哪台设备、哪个 Agent（类型/版本/等级）、用了什么能力/工具、数据密级、命中了哪条策略及处置、调用了哪个模型、token 与成本、结果状态
- 日志本身即敏感数据：落盘前脱敏，原文捕获默认关闭、仅排障时单独开启（AstrLink 的做法）
- 防篡改：哈希链或 WORM 存储；按用户检索"违规全链"、一键解封/封禁（VGuard 的运营体验）
- 冷热分层与保留：热存短周期，过期 zstd 压缩 NDJSON 归档，保留期按合规要求配置（借鉴幻城归档参数作为默认模板）
- 异常检测与告警：短时大量外发、非工作时间高密级调用、单用户违规激增 → 告警 Webhook（HMAC 签名）
- 导出对接：SIEM（Syslog/ Splunk）、对象存储归档；按团队可关闭内容日志（仅留元数据，GDPR 式取舍）
- 合规报表：面向等保三级 / ISO 27001 的检查项映射与证据导出（WorkBuddy 企业版以等保三级为锚，我们的开源版至少提供自检清单）

## 4. 与各家的差异化对照

| 对比对象 | 它做不到 / 不做的 | 我们的做法 |
|---|---|---|
| New API | 只管模型流量；不管端侧 Agent、不管加密文件、不管能力/MCP 治理；设置明文存库 | 防护延伸到端侧+能力侧；密钥加密托管；加数据分级路由 |
| WorkBuddy 企业版 | 绑自家 Agent 与腾讯生态；闭源，靠厂商信任（含可信计算） | 开源可审计、中立不绑 Agent、自托管，信任来自代码而非厂商承诺 |
| Cloudflare AI Gateway | 托管形态，流量过第三方；不能离线 | 全自托管，可完全离线运行 |
| LiteLLM Enterprise | 企业功能闭源收费；无 Agent/能力层 | 企业治理功能开源；覆盖 Agent 与能力层 |
| dsh-ee（原版） | 绑 DSH；防护以审核+权限+审计为主，无 DLP/脱敏/分级路由管线 | 不绑 Agent；网关防护管线 + 端侧隐私网关 + 分级路由为核心卖点 |

---

## 5. 落地路线（建议）

### MVP（第一期，先跑通"管得住"）
- 身份：本地账号 + OIDC，部门 RBAC，分级令牌（受管/自带两级先行）
- 网关管线：鉴权 → 限流配额 → 敏感词过滤 → 规则级 DLP（凭据/PII/自定义词表）→ 拦截/脱敏二选一策略 → 按通道信任类型分级的路由（签约云 / 脱敏后上云 / 专有云-VPC / 本地小模型），无合规通道时明确拦截并提示 → 审计
- 审计：结构化日志 + 按用户/部门检索 + 导出
- 管理面：策略配置 UI 含试运行模式；密钥加密存储；SSRF/CORS/登录锁定等基线加固
- 接入：setup 脚本自动给 DSH / WorkBuddy / Claude Code 等写网关配置（薄适配）

### 第二期（"防得深"）
- 端侧本地隐私网关 sidecar：规则+本地小模型检测、可逆脱敏与响应还原
- Agent 证明（版本/配置哈希/插件清单）与受管 Agent 包、加密文件白名单对接方案（白皮书+配置指南）
- MCP 工具级授权与工具返回 DLP；技能供应链扫描与签名
- 审核模型复审（同步/异步）、违规全链运营台、日志冷热归档与防篡改

### 第三期（"过合规"）
- 异常行为检测与告警、SIEM 对接
- 等保/ISO 自检清单与合规报表
- 可选可信计算/机密模型对接（对接厂商 TEE 推理，而非自研）

## 6. 待决策的问题

1. **脱敏执行点**：端侧脱敏（数据不出本机，体验好，但依赖端侧可信）与网关脱敏（集中可控，但明文已到网关）如何分工？建议：受管级走端侧+网关双层，自带级强制网关脱敏。
2. **可逆映射的保管**：占位符映射表放本机（AstrLink 式）还是企业 Vault？前者隐私最好，后者便于跨设备续接。建议默认本机，企业可策略切换。
3. **响应侧 DLP 的延迟取舍**：流式缓冲扫描显著增加首 token 延迟，建议仅高密级部门/模型开启，并在文档中明示。
4. **检测模型选型**：自训小模型（参考 AstrLink Guard 的体量与类目）还是接开源 NER（如 Presidio/GLiNER）？建议一期规则+Presidio 式 NER，二期评估自训。
5. **与加密软件厂商的关系**：是否要针对主流透明加密厂商做兼容性验证清单（哪些版本、哪种白名单粒度），这会直接影响企业落地意愿。
