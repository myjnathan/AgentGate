# 双机热备与高可用（F27）——方案评审与阶段一

> 状态：方案评审（2026-11-24）通过；阶段一（主备 + 单写锁 + 就绪探针）已落地。
> 后续阶段见 §7。队列：F27 仍为唯一剩余条目，下一轮继续阶段二。

## 1. 目标与非目标

**目标**（backlog F27 原文）：网关无状态化 + 状态外置或主备切换，单点故障时
受管调用不中断、审计不丢失；对应弱点清单 #3（单点故障）。

本轮把目标量化为两项可验收的指标：

- **RTO（恢复时间目标）**：主节点进程死亡后，备节点接管并恢复服务的时间
  ≤ 1 分钟（实测：锁释放是内核行为、进程死亡即释放；接管耗时 = 备节点
  启动 + 重读状态 + 验链，通常数秒）。
- **RPO（恢复点目标）**：阶段一为「最后一次已完成写入」——即 `state.json`
  最后一次原子替换与 `audit.jsonl` 最后一次追加写；**不承诺零丢失**
  （见 §6 诚实边界：写路径无 fsync，硬掉电可能丢最后一次写入窗口）。

**非目标**（本轮不做）：多活（两个节点同时服务）、跨机房 / 跨可用区、
状态外置到外部数据库、审计零丢失（fsync + 同步复制，阶段二/三）。

## 2. 状态盘点——接管时什么要续上、什么可以丢

接管的本质是：备节点在**不重建世界**的前提下继续服务。先盘点全部状态：

### 2.1 持久化状态（在数据目录里，接管时重读）

| 状态 | 文件 | 写入方式 | 接管行为 |
| --- | --- | --- | --- |
| 平台配置与业务数据（用户/渠道/令牌/策略/词表/预算/知识包/例外/报表…） | `state.json` | 整文件原子替换（写 tmp + rename，0600） | 备节点启动时重读最后一份完整快照；替换是原子的，读到的要么是旧快照、要么是新快照，永不读到撕裂文件 |
| 审计日志（哈希链） | `audit.jsonl` | 追加写，每事件一行 | 备节点启动时重读全链、续接链头（`PrevHash` = 旧链尾哈希）；验链失败则拒绝接管（§5.4） |
| 安装包与上传分片 | `packages/`（F20） | 文件落盘 | 随数据目录共享；断点续传会话在 `state.json` 里，随快照一起续上 |
| 审计归档段 | `audit-archive-*.jsonl.gz` + 清单（F4） | 归档时写出 | 随数据目录共享；归档检查点事件同样续接（见 `verifyEvents`） |
| 主密钥 | 不落盘（启动时环境变量传入） | — | 两节点须配**同一主密钥**，否则备节点解不开渠道密钥与令牌；部署时由同一密钥源下发 |

### 2.2 运行时状态（只在内存里，接管时重建、可接受丢失）

| 状态 | 接管后行为 | 影响 |
| --- | --- | --- |
| 渠道健康 / 冷却（F1） | 清零重建 | 故障渠道可能被短暂重试一次，由 F1 熔断重新收敛；不影响正确性 |
| 渠道密钥轮询游标（F12） | 从第一把密钥重新开始 | 无影响（轮询顺序变化而已） |
| 限流计数（F3，60 秒滑动窗口） | 清空 | 切换窗口内限流短暂放宽 60 秒以内；可接受（限流是配额控制，不是安全边界） |
| 响应缓存（F11） | 清空 | 首批请求回源一次；缓存只存公开/内部干净响应，无正确性影响 |
| OTel 待导出 span 队列 | 丢失 | 遥测丢失，不影响业务与审计 |
| 文件夹知识库索引（F18）与语义索引（F19） | 启动时重扫重建 | 启动稍慢；索引重建期间知识工具暂不可用（与单节点重启一致） |
| 终端在线状态（F23） | 由下一次心跳重建 | 切换后 5 分钟内终端可能显示 offline，属已知表现 |
| 告警投递队列（F5） | 丢失未投递项 | 切换窗口内的告警可能少发一条；审计事件本身不丢（在 `audit.jsonl` 里） |
| 例外凭证「已使用」标记 | 在 `state.json` 里，随快照续上 | 一次性凭证不会因切换被重复使用（标记是持久化状态） |

**结论**：没有哪一项运行时状态的丢失会破坏分级 / 脱敏 / 审计红线。
接管只需保证两件事：**同一时间只有一个写者**（§5.1），以及**审计链不断叉**
（§5.4）。

## 3. 故障模型

| 故障 | 阶段一的处置 |
| --- | --- |
| 主节点进程崩溃 / 被 kill（含 SIGKILL） | 内核释放 flock；备节点获锁后接管 |
| 主节点主机宕机 | 同上（锁随主机死亡而释放；共享卷须由存储层保证可达） |
| 主节点磁盘满（state/audit 写失败） | 不触发接管（锁仍在主手里）；`/readyz` 变 503，负载均衡器排空该节点流量（§5.3）；运维介入清盘 |
| 共享卷丢失 / 损坏 | 双节点同坏——阶段一不解决（卷本身是单点，见 §6）；靠卷快照 / 阶段三的异地复制兜底 |
| 网络分区（主备之间） | 两节点不直接通信，无分区可言；分区只影响「备能否看到共享卷」——看不到卷的备拿不到锁（锁文件在卷上），不会脑裂 |
| 脑裂（两个写者同时写） | 由单写锁从机制上杜绝（§5.1）；前提是锁文件不被手动删除（§6） |

## 4. 方案比较——为什么阶段一选「主备 + 共享卷 + 单写锁」

| 方案 | RTO | RPO | 复杂度 | 取舍 |
| --- | --- | --- | --- | --- |
| **A. 主备 + 共享数据目录 + 单写锁（本轮）** | 秒级～1 分钟 | 最后一次已完成写入 | 低：一个 flock + 一个探针，无新依赖 | 共享卷是单点；只防进程/主机死，不防卷坏 |
| B. 状态外置：SQLite（WAL）+ Litestream 异步复制到对象存储 | 分钟级（恢复 + 重放） | 约 1 秒（同步间隔） | 中：引入 SQLite 与复制 sidecar，state.json 需迁移 | 是灾备、不是高可用——Litestream 官方定位即「disaster recovery, not high availability」，复制是异步的，盘坏仍丢最后约 1 秒写入（litestream.io/how-it-works） |
| C. Raft 多活（etcd / hashicorp raft） | 秒级 | 零（多数派提交） | 高：共识、成员变更、选主、日志复制全套；与单二进制零依赖定位冲突 | 能力最强，但工程量与运维成本超出目标客户（无专职 IT 的传统公司）的承受范围 |
| D. 定时备份 + 手动恢复 | 小时级 | 上次备份 | 最低 | 不是热备；只作为所有方案的最后兜底（已有 `state.json` 拷贝 + 审计归档即备份） |

**决策**：阶段一做 A。理由有三：① 现有持久化形态已经是接管友好的——
`state.json` 是原子替换、`audit.jsonl` 是追加链，接管 = 重读 + 验链，
不需要改存储格式；② 零新依赖，符合单二进制定位；③ B 是 A 的自然演进
（共享卷换成「SQLite + 对象存储复制」），C 是远期选项，路线不冲突。
B/C 的评估留待 §7。

借鉴点（一手来源，2026-11-24 查阅）：

- Kubernetes 官方文档《Liveness, Readiness, and Startup Probes》
  （kubernetes.io/docs/concepts/workloads/pods/probes）：三类探针分工——
  存活探针（liveness）只判「进程是否陷入不可恢复状态」，失败则重启容器，
  **不得检查外部依赖**；就绪探针（readiness）判「现在能否接流量」，
  失败只把 Pod 从 Service 端点摘掉、**不重启**，恢复后重新加回。
  我们照此分工：`/healthz` 保持原样（进程活着即 200，作 liveness），
  新增 `/readyz` 作 readiness（检查写健康与启动时链校验，失败只排空流量）。
- Litestream 官方《How it works》（litestream.io/how-it-works）：
  以 WAL 页为单位异步流式复制、按 TXID 组织 LTX 文件、定期快照；
  明确说明异步复制的 RPO 边界（「if the disk dies you can lose the
  last second or so of writes」）与「single writer per replica path」。
  我们借其两点：① 阶段三的状态外置走同一形态（WAL 复制 + 快照）；
  ② RPO 的诚实表述方式——异步即有窗口，不宣称零丢失。

## 5. 阶段一设计（已落地）

### 5.1 单写锁：`AGENTGATE_HA_MODE=active|standby`

- 锁文件：数据目录下的 `agentgate.lock`，进程启动时（`store.New` 之前）
  打开并加 `flock(LOCK_EX)`。
- `active`（默认）：非阻塞加锁；锁被占时立即退出并打印明确原因，
  提示改用 `standby` 模式。——防止误起第二个实例悄悄双写
  `state.json` / 分叉审计链（此前无任何防护）。
- `standby`：阻塞等待锁；主节点死亡、内核释放锁后自动获锁并继续启动
  （先到先得：最先获锁的备节点成为新的 active）。
- 锁随进程持有：正常退出、崩溃、SIGKILL 都会释放（内核行为，不依赖
  进程清理）；**不要手动删除锁文件**——flock 锁在 inode 上，删文件后
  新进程会建出新 inode 并拿到「另一个锁」，双写防护即失效。
- 平台限制：flock 是 Unix 语义（Linux/macOS）；Windows 构建上锁为
  no-op（单节点部署不受影响，HA 部署只支持 Linux）。

### 5.2 接管流程（备节点视角）

1. 启动，`AGENTGATE_HA_MODE=standby`，阻塞等锁；
2. 获锁（主已死），日志记 `ha: took over as active`；
3. `store.New` 重读 `state.json`（最后一份完整快照）；
4. `audit.Open` 重读 `audit.jsonl`，续接链头；
5. 验链（`Verify()`）：通过则继续启动，失败则**拒绝接管、直接退出**
   （fail-closed，见 §5.4）；
6. 正常启动（文件夹重扫、语义索引重建等与单节点重启一致），开始服务。

### 5.3 探针：`/healthz` 与 `/readyz`

| 探针 | 语义（K8s 分工） | 检查项 | 失败动作 |
| --- | --- | --- | --- |
| `GET /healthz`（已有） | 存活：进程是否活着 | 无（进程能响应即 200） | 编排器重启容器 |
| `GET /readyz`（新增） | 就绪：现在能否接流量 | ① `state.json` 最近一次保存无错误；② `audit.jsonl` 最近一次追加无错误；③ 启动时审计链校验通过 | 编排器把节点从服务端点摘掉（不重启）；恢复后重新加回 |

就绪检查的两个写健康信号来自本轮新增的可见性：此前 `audit.Append`
与各处 `store.Save()` 的错误都被静默吞掉（`_ =`），写失败时进程
表面一切正常。本轮起 `audit.Log.LastError()` 与 `store.Store.LastSaveError()`
记录最近一次写错误（成功则清零），供 `/readyz` 读取；`Problems()` 只
返回类别码（`state_save_failed` / `audit_append_failed` /
`audit_chain_invalid`），不含路径与原文。

响应：就绪 `200 {"ready":true}`；未就绪 `503 {"ready":false,"problems":[...]}`。

### 5.4 审计连续性规则

- 接管后新事件的 `PrevHash` 续接旧链尾哈希（`audit.Open` 从文件重算链头），
  历史不改写、不截断；归档检查点事件同样续接（`verifyEvents` 的检查点语义不变）。
- 接管时先验链：链已断（文件被改过 / 磁盘损坏）时备节点拒绝启动，
  运维须先从归档段恢复 `audit.jsonl`（见 `docs/audit-retention.md` 的
  离线验真与归档恢复），再重启备节点。——宁可无服务，不可把断链再延长。
- 主节点正常启动时同样验链并记日志；链断时只告警、不退出（保持单节点
  既有行为：此前无启动验链，老部署不因升级而无法启动），但 `/readyz`
  同样报 `audit_chain_invalid`，由编排器排空流量。

### 5.5 什么没变

- 分级 / 脱敏 / 审计红线不变；网关、MCP、sidecar 的行为不变。
- 单节点部署默认 `active`，行为与升级前一致（多一个锁文件与一个探针端点）。
- 冒烟与既有测试不受影响（冒烟用 `mktemp -d` 的数据目录）。

## 6. 诚实边界——阶段一**不**保证什么

- **RPO 不是零**：`audit.Append` 与 `store.Save` 均无 fsync（与升级前一致，
  刻意不改：逐事件 fsync 会给每次调用加一次磁盘同步，属性能取舍）。
  硬掉电（非进程崩溃）可能丢最后一次写入窗口内的事件 / 配置变更。
  进程崩溃（非掉电）时 OS 页缓存仍在，数据不丢。
- **共享卷是单点**：卷坏、卷满、卷不可达时双节点同坏；阶段三才引入异地复制。
- **锁只防双写，不防「主活着但不健康」**：主节点磁盘满、链已断时锁仍在
  主手里，备节点不会接管；此时靠 `/readyz` 排空流量 + 运维介入，
  不是自动切换。租约 / 心跳式接管（主活但失联即夺锁）是阶段二课题，
  需先解决「误判夺锁导致双写」的防护，本轮不做。
- **切换期间在途请求失败**：主死时正在处理的请求由客户端重试
  （上游模型调用本身也可能已发出一次；幂等性由调用方保证，与单节点
  重启一致）。
- **flock 在 NFS 上依赖 lockd / NFSv4**：NFSv3 且无 lockd 的共享卷上锁
  不可靠；部署要求：本地盘、NFSv4 或支持 flock 的集群文件系统。
- **Windows 无单写锁**：HA 部署只支持 Linux。

## 7. 后续阶段

- **阶段二（下一轮候选）**：① 写路径 fsync 选项（`AGENTGATE_AUDIT_FSYNC=1`，
  审计追加写后同步落盘，把硬掉电 RPO 收窄到「最后一次 fsync 之后」，
  代价是每次调用多一次同步，默认关闭、由管理员按需开启并实测性能）；
  ② 备节点预热：standby 等锁期间定期重读 `state.json`（只读），
  缩短接管后的启动时间（文件夹索引仍须接管后重建）；③ 评估租约式接管。
- **阶段三（远期）**：状态外置——`state.json` 迁到 SQLite（WAL 模式），
  Litestream 式异步复制到对象存储（灾备 + 异地恢复）；审计日志同步归档
  到对象存储；届时重新评估 Raft 多活的必要性（目标客户无专职 IT，
  多活的运维成本可能长期大于收益）。
- **贯穿**：每次切换演练（kill 主 → 观察备接管 → 验链 → 抽查调用）
  应进发布检查清单；演练步骤见 §8。

## 8. 部署示例与运维

### 8.1 systemd 双节点（共享卷 `/mnt/agentgate-data`，NFSv4）

```ini
# /etc/systemd/system/agentgate-primary.service
[Service]
Environment=AGENTGATE_DATA=/mnt/agentgate-data
Environment=AGENTGATE_MASTER_KEY=<同一主密钥>
Environment=AGENTGATE_HA_MODE=active
ExecStart=/usr/local/bin/agentgate
Restart=always
```

```ini
# /etc/systemd/system/agentgate-standby.service（另一台机器，同一共享卷）
[Service]
Environment=AGENTGATE_DATA=/mnt/agentgate-data
Environment=AGENTGATE_MASTER_KEY=<同一主密钥，与主节点相同>
Environment=AGENTGATE_HA_MODE=standby
Environment=AGENTGATE_ADDR=127.0.0.1:8788
ExecStart=/usr/local/bin/agentgate
Restart=always
```

两节点须用**同一主密钥**（否则备节点解不开渠道密钥），且共享卷须
支持 flock。前端负载均衡只把流量发给 `/readyz` 为 200 的节点。

### 8.2 Kubernetes 探针示例

```yaml
livenessProbe:
  httpGet: {path: /healthz, port: 8787}
  periodSeconds: 10
readinessProbe:
  httpGet: {path: /readyz, port: 8787}
  periodSeconds: 5
  failureThreshold: 3
```

### 8.3 切换演练

1. 主节点 `kill <pid>`（或停服务）；
2. 备节点日志出现 `ha: took over as active`，`/readyz` 变 200；
3. `GET /api/audit/export` 导出并验链（`X-Audit-Chain-Valid: true`）；
4. 抽查一次模型调用与一次 MCP 工具调用均正常；
5. 原主节点以 `standby` 模式重新启动，成为新的备节点。

### 8.4 链校验失败拒绝接管时

1. 停下备节点（不要强行启动）；
2. 按 `docs/audit-retention.md` 从归档段恢复 `audit.jsonl`，
   或从卷快照恢复整个数据目录；
3. 恢复后重启备节点（仍为 `standby`），验链通过即接管。
