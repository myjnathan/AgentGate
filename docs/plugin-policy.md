# 插件管控设计（F38）

Nathan 2026-11-26 指示立项：限制员工桌面 Agent（以 DSH 为首）可安装的插件，
实现白名单与黑名单管控。本文是设计稿，随切片落地同步更新。

## 1. 目标与非目标

目标：管理员能回答并控制三件事——全网装了哪些插件、哪些不许装、
装了不许装的插件会怎样。管控对象是经 AgentGate 受管的桌面 Agent
（DSH、Claude Code、Codex 等）上报的插件清单，不绑定某一种 Agent。

非目标：不做终端 EDR 式的文件系统强制拦截（删除/隔离员工机器上的文件）；
不盘点 Agent 之外的软件（与终端盘点「只盘 Agent」的既定边界一致）。

## 2. 现状与缺口

已有地基：

- F14 证明策略（`internal/attest`）已有 `AllowedPlugins` / `BlockedPlugins`
  字段与评估理由码 `blocked_plugin` / `plugin_not_allowed`，登录证明时比对，
  不符自动降级自带级 + 告警。
- 终端持续盘点（`internal/terminal`）心跳已上报插件清单，漂移评估含
  「禁用插件」判定。

缺口：

1. 只按**名字**匹配（大小写不敏感）——改名、换版本、内容被篡改都绕得过。
2. 名单埋在证明策略里，没有独立的策略对象、作用域与管理界面。
3. 没有全网插件资产视图：管理员看不见「谁装了什么」。
4. 处置只有「降级」一档，没有观察→告警→降级→断敏感能力的梯度。
5. 只有装后发现，没有安装前校验。

## 3. 插件标识：三元组

插件以 **（ID、版本、内容哈希 SHA-256）** 三元组标识。名单规则可只写 ID
（管全部版本）、ID+版本约束（`>=`、精确）、或 ID+版本+哈希（最严，
内容被篡改即不符）。

兼容：旧版 Agent 只上报名字时，按名匹配并在资产视图标注「未验证」
（无版本/哈希证据），管理员可据此推动升级，不直接判违规。

## 4. 策略模型

`PluginPolicy` 为独立策略对象：

- **模式**：`allowlist`（默认拒绝，名单外即违规；保守模式预设用此）或
  `denylist`（默认允许，名单内违规；必须同时开启未知插件告警，
  否则改名即绕过、形同虚设）。
- **规则**：插件三元组 + 来源约束 + 备注 + 生效/失效时间。
- **来源约束**：插件须来自平台分发渠道（F20 包分发，包哈希作基准）；
  公网市场、本地文件等其他来源在 allowlist 模式下默认违规。
  「管装什么」与「管从哪装」一起才闭环。
- **作用域**：全局 → 部门 → 用户组逐层继承，**只能收紧不能放宽**
  （下级可新增禁止、不可解除上级的禁止；白名单同理只能缩小）。
- **处置梯度**（每策略可选）：`observe` 只记录 → `warn` 告警 →
  `downgrade` 降级自带级 → `block_sensitive` 在降级基础上断机密通道
  与敏感能力，直至整改（卸载违规插件且心跳复核通过自动恢复）。

## 5. 执行三层

1. **盘点（看得见）**：复用终端心跳上报的插件清单，平台聚合为资产视图：
   插件 × 版本 × 装机量 × 合规状态 × 涉及终端/用户。
2. **准入（进不了敏感的门）**：复用 `attest` 评估，理由码扩展：
   `blocked_plugin`、`plugin_not_allowed`（已有）、`plugin_version_mismatch`、
   `plugin_hash_mismatch`、`plugin_unknown_source`（新增）。登录证明与
   持续心跳共用同一评估函数，判定口径处处一致。
3. **安装前校验（装之前拦住）**：平台提供
   `POST /api/plugin/check`（入参：Agent 身份 + 插件三元组 + 来源；
   出参：allow/deny + 理由）。Agent 安装插件前调用，deny 则不装。
   **此层依赖 Agent 侧接入**：DSH 接了才是装前阻断；不接则只有
   第 1、2 层（装后发现 + 降级），见 §7 边界。

## 6. 例外通道

员工确需名单外插件时，走已有例外审批流（`internal/exception`）：
申请（插件三元组 + 理由）→ 管理员批准 → 生成带期限的例外规则，
到期自动失效，全程进哈希链审计。没有例外通道，白名单会被业务
逼着开大洞，最终失效。

## 7. 边界与弱点（明说）

- 插件清单是 Agent **软件自报**证据，与 F14 同一已知限制：能防无意
  违规与配置漂移，不防有意伪造上报的内鬼；防伪造需 Agent 侧签名
  上报，列为后续评估。
- 安装前阻断依赖 Agent 侧调用校验接口；AgentGate 单方只能做到
  装后发现 + 降级 + 断敏感能力，做不到替员工的机器删文件。
- 员工在个人设备或用便携版 Agent 完全绕开受管体系，不在本功能
  范围内，归客户保密制度与管理手段（与「只防电脑内的数字数据流」
  的总边界一致）。
- denylist 模式天然可被改名绕过，产品上必须与未知插件告警绑定
  销售与默认配置，不得单独宣传为「管控」。

## 8. 管理台

两页，遵循体验总原则（系统能判断的不留给用户）：

- **插件策略页**：模式、作用域、名单维护；名单可从资产视图
  「一键加入」（系统已盘到的插件不必手打 ID/哈希）。
- **插件资产页**：全网聚合视图，违规项标红并可直达处置与例外审批。

## 9. 切片计划

- 切片 1：`PluginPolicy` 策略对象 + `attest` 评估升级（三元组、版本/哈希
  匹配、新理由码）+ 管理台插件策略页。**已完成（2026-11-26）**：策略对象、
  三元组评估与策略页均已落地并合并；评估在登录批准与心跳共用同一函数。
  落地时定的三点：① 提交时预览不跑插件评估（作用域需审批人部门，批准时
  重评为准）；② 用户组作用域已定义但暂不生效（无用户组成员模型）；
  ③ `block_sensitive` 本切片与降级相同，强制执行随切片 2。
- 切片 2：插件资产视图 + 处置梯度（含整改自动恢复）。
- 切片 3：例外审批打通（插件类型）+ 安装前校验接口
  `POST /api/plugin/check`。
