## 1. 要解决的问题

阶段一（主备 + 单写锁 + `/readyz`）与阶段二（fsync 选项 + 备节点预热）已经解决的故障：

- 主节点进程崩溃 / 被 kill（含 SIGKILL）→ 备节点秒级接管（实测约 2–5 秒）；
- 写健康可见（`/readyz` 503 排空流量）；
- 硬掉电 RPO 收窄到最后一次已完成的调用 / 保存（`AGENTGATE_FSYNC=1`）。

阶段三要解决的，是上面两阶段**没有解决、也不可能解决**的故障：

| 未解决的故障 | 现状后果 |
| --- | --- |
| 共享卷损坏 / 丢失 | 双节点同坏——`state.json` 与 `audit.jsonl` 都在卷上 |
| 共享卷满 / 不可达 | 双节点同时写不动，`/readyz` 排空后无节点可接流量 |
| 硬掉电（默认无 fsync） | 可能丢最后一次写入窗口 |
| 主节点"活着但不健康" | 锁仍在主手里，备不接管（阶段二 §9 已评估租约式接管，结论不采用） |
| 切换期间在途请求 | 失败，由客户端重试 |

一句话：**阶段一/二防的是"节点死"，阶段三防的是"卷死"。** 卷坏是低频事件，但一旦发生就是全量数据丢失——这是阶段三唯一要补的缺口。不要为它付出超过其发生概率的代价，也不要把它包装成"接管更快"：阶段一/二的接管已经是秒级，阶段三的恢复注定是分钟级（见 §3 B）。

## 2. 约束——先定边界，再选方案

- **目标客户**：无专职 IT 的传统中小公司（见蓝图与 F17/F18 立项背景：没有自有模型、没有数据库、没有知识库）。任何要求客户多管一个数据库、多管一个 sidecar、多做一次恢复演练的方案，都要先问一句"客户管得过来吗"。
- **产品定位**：单二进制 + 零外部依赖。引入外部依赖（数据库、对象存储、复制 sidecar）是定位让步，必须有对应的收益才值得。
- **主密钥不落盘**：两节点须配同一主密钥（见 ha-design.md §2.1），阶段三不改变这一点——恢复出来的新节点同样要拿到主密钥才能解开渠道密钥与令牌。
- **审计链不断叉**：任何复制/恢复方案都必须保证 `audit.jsonl` 的哈希链续接与验链规则（ha-design.md §5.4），恢复后链断 = 拒绝启动。

## 3. 候选形态对比

### A. 维持现状：共享卷主备 + 备份与演练加固（零代码）

- **内容**：不动架构、不引依赖。只补三件制度化的事：① 定期卷快照（存储层能力）；② `state.json` + `audit.jsonl` + 审计归档段定时离线备份到异地（可以就是管理员的另一台机器或网盘，不必是对象存储）；③ 每季度一次切换演练进发布检查清单（ha-design.md §8.3 的步骤照跑一遍）。
- **RPO**：上次备份（小时～天级，看备份频率）。
- **RTO**：小时级（手动恢复：取回备份 → 验链 → 重启）。
- **成本**：零新依赖、零代码、零运维新增——备份是管理员本来就该做的事。
- **诚实点**：这不是高可用，是灾备。卷坏 = 停机 + 手动恢复 + 丢上次备份以来的数据。对目标客户而言，卷坏是低频事件，这个代价可能是可接受的；但"可接受"必须由 Nathan 拍板，不能由 Loop 默认。

### B. 状态复制：SQLite WAL + Litestream 式异步复制到对象存储（backlog 原定形态）

- **内容**：`state.json` 迁到 SQLite（WAL 模式）；Litestream 式 sidecar 把 WAL 页以 LTX 文件异步复制到对象存储（S3 兼容）；审计日志同步归档到对象存储；卷坏 / 整机坏后在新机上 restore + 验链 + 重启。
- **一手来源（2026-11-24 查阅）**：
  - **Litestream 官方《How it works》（litestream.io/how-it-works）与恢复指南**：Litestream 是跑在应用旁边的独立进程，把数据库置于 WAL 模式后持续读 WAL、把新页以 LTX 文件上传到副本；定期取完整快照（默认每 24 小时）；恢复 = 最新快照 + 重放其后的 LTX；支持按时间点恢复（`litestream restore -timestamp`），但最细的恢复点只在 L0 文件保留期内存在（默认压实后 5 分钟），快照默认保留 24 小时；默认同步间隔约 1 秒，**硬崩溃最多丢约 1 秒写入**；"single writer per replica path"——两个实例绝不能复制到同一个桶/路径，否则可能无法恢复；Litestream 自我定位是**备份与恢复工具，不是高可用方案**（"disaster recovery, not high availability"）；最关键的一句：**副本不是可查询的热库**，它只是 S3 里的 WAL 流与快照归档，必须用 `litestream restore` 物化成文件才能用。
  - **SQLite 官方《Write-Ahead Logging》（sqlite.org/wal.html）**：WAL 模式下提交追加进 WAL 文件、读不阻塞写；检查点（checkpoint）把 WAL 内容搬回数据库文件，默认 WAL 达到 1000 页时自动检查点；决定性约束——**"All processes using a database must be on the same host computer; WAL does not work over a network filesystem"**：WAL 模式的数据库文件必须在本地盘上，不能放 NFS 共享卷。也就是说，阶段三的双节点必须**各用本地盘 + 复制**，共享卷架构要改；flock 跨节点互斥也随之失效。
- **RPO**：约 1 秒（异步复制窗口）。
- **RTO**：分钟级（restore + 验链 + 重启），不是秒级接管——**B 是灾备，不是热备**，不替代阶段一/二的秒级接管，而是兜底。
- **成本**：中等。引入 SQLite（Go 驱动选型待实测：modernc.org/sqlite 纯 Go 更合单二进制定位，mattn/go-sqlite3 需 cgo）+ Litestream sidecar（二进制或 Go 库嵌入，Apache-2.0）+ 对象存储（选型未定：S3 / 阿里云 OSS / Cloudflare R2 / MinIO 自托管）+ 状态迁移（`state.json` → SQLite 表结构 + 迁移脚本 + 回滚方案）。
- **风险与诚实点**：
  - 复制是异步的，RPO 不是零；宣称零丢失是错的。
  - 审计链不在 SQLite 里：`audit.jsonl` 是追加日志，不能直接进 WAL 复制；需单独的对象存储归档通道（F4 已有本地 gzip 归档，缺上传）；恢复时审计链的续接与验链规则要重写。
  - 双写防护要重做：本地盘之后 flock 不再跨节点生效；需要 epoch / fencing（阶段二 §9 已评估：租约 + epoch 的重评条件是时钟 NTP 同步可验证、fencing 落到每次写路径、故障注入演练先行）。
  - 对象存储本身成为新单点：桶删、凭证丢、欠费停服 = 备份丢；需版本控制 + 凭证加密存储（红线：密钥只加密存储、不回显）+ 异地桶。
  - 运维成本：目标客户要多管一个 sidecar + 一个桶 + 恢复演练；管不过来时，B 的收益为负——备份没验过恢复等于没备份。

### C. 外部存储：状态外置到外部数据库 / 对象存储上的状态文件

- **内容**：`state.json` 迁到外部数据库（托管 Postgres / MySQL）或对象存储上的状态文件；网关进程变成无状态，任意节点可起。
- **RPO / RTO**：取决于外部库自身的备份与高可用（托管库通常有自动备份与主备，RPO 分钟级、RTO 分钟级）。
- **成本**：高。违背"单二进制 + 零依赖"定位：客户要多部署 / 多买一个数据库；连接、凭证、网络、备份全是新运维面；`state` 的读写模式（整文件快照）要改成行级读写，是全仓存储层重构。
- **诚实点**：这是把单点从共享卷搬到数据库，问题没有消失，只是换了责任方。对目标客户（没有数据库，见 F17/F18 的立项背景）尤其不合适——让客户先买数据库再用网关，与产品定位直接冲突。
- **结论：不推荐。**

### D. Raft 多活（对照项，复评）

- **内容**：etcd / hashicorp raft，共识、选主、日志复制；RPO 零（多数派提交）、RTO 秒级。
- **成本**：最高。共识、成员变更、选主、日志复制全套；与单二进制零依赖定位冲突；目标客户运维不起。
- **结论：不推荐。** 远期重评条件不变（ha-design.md §4）：只有目标客户画像变了（有专职 IT、能运维共识集群）才重评。

## 5. 推荐（明确）

**推荐：A 立即做 + B 分两步走，但 B 只做"备份级"、不做"热备级"；不做 C、不做 D。**

- **A（立即做，零代码）**：备份与演练制度化——卷快照 + 离线备份 + 每季度切换演练。这件事不依赖任何选型，现在就能写进部署文档（`docs/ha-design.md` §8 演练步骤已现成，缺的是"定期备份"一节）。
- **B1（下一步，备份级）**：对象存储只做异地备份，不动存储格式、不引 SQLite、不动接管路径——审计归档段（F4 已有本地 gzip 归档）上传对象存储 + `state.json` 定时快照上传对象存储 + 从对象存储取回并验链的恢复演练。RPO 小时级、RTO 小时级（手动恢复），但卷坏不再丢全部数据。B1 是 B 的一半工作量，却拿到 B 的大部分收益（卷坏可恢复）。
- **B2（按需，复制级）**：`state` 迁 SQLite WAL + Litestream 异步复制。只有同时满足三个条件才启动：① B1 已跑顺（备份与恢复演练已成习惯）；② 对象存储选型已定；③ 有真实客户提出卷坏恢复需求（RPO 小时级不够用）。三个条件缺一个，B2 就不启动。
- **不做 C、不做 D**：理由见 §3（定位冲突、运维成本超出目标客户承受范围）。
- **关键判断**：阶段三的真实收益是"卷坏可恢复"（灾备），不是"接管更快"（阶段一/二已秒级）。不要为灾备付出热备的代价，也不要把异步复制包装成零丢失。

## 8. 诚实边界——阶段三**不**保证什么

- 异步复制的 RPO 不是零（B 的窗口约 1 秒）；恢复的 RTO 是分钟级（restore + 重启），不是秒级接管。
- 对象存储是新单点：桶删、凭证丢、欠费停服 = 备份丢；缓解靠版本控制、凭证加密存储与异地桶，不是靠"选了对象存储就安全了"。
- 备份没验过恢复等于没备份：A 与 B1 的验收都是"取回来、验链通过、服务起来"，不是"备份任务跑通了"。
- 阶段三不解决：切换期间在途请求失败（仍由客户端重试）、主活但不健康不接管（仍靠 `/readyz` 排空 + 人工介入）。
- 阶段一/二的诚实边界（ha-design.md §6）继续有效：共享卷是单点（A/B1 下仍是）、fsync 只保已完成写入的持久性。

## 10. 一手来源与复用检查

- **Litestream 官方《How it works》（litestream.io/how-it-works，2026-11-24 查阅）**：WAL 页异步流式复制、TXID 组织 LTX 文件、定期快照；明确说明异步复制的 RPO 边界（盘坏丢最后约 1 秒写入）与"single writer per replica path"；自我定位是灾备而非高可用。
- **Litestream 恢复指南（litestream.io，2026-11-24 查阅）**：恢复 = 最新快照 + 重放其后 LTX；`-timestamp` 时间点恢复；最细恢复点只在 L0 文件保留期内（默认压实后 5 分钟），快照默认保留 24 小时；副本不是可查询的热库，须 restore 成文件才能用。
- **SQLite 官方《Write-Ahead Logging》（sqlite.org/wal.html，2026-11-24 查阅）**：WAL 提交追加进 WAL 文件、检查点把内容搬回数据库文件、默认 1000 页自动检查点；"All processes using a database must be on the same host computer; WAL does not work over a network filesystem"——WAL 模式须用本地盘，是阶段三"双节点各用本地盘 + 复制"这一形态的决定性依据。
- **复用检查（Nathan 复用优先指示）**：本轮只产出评审文档，未复制、未引入任何代码；Litestream 为 Apache-2.0（与 AGPL-3.0 兼容），若将来 B2 采用其实实现（sidecar 二进制或 Go 库嵌入），须在 DEVLOG 记录来源项目、文件与许可证。
