# 开发 Loop 协议（Development Loop）

AgentGate 由一个定时 Loop 持续推进开发（Nathan 于 2026-11-21 授权，全权执行）。
本文档是 Loop 每轮运行的固定规程，任何一轮都按此执行，保证**可持续、可审计、可回滚**。

## 节奏
- 每 1 小时一轮（Asia/Shanghai，2026-11-21 Nathan 由每 2 小时改为每小时），每轮只做**一件事**：backlog 中优先级最高的一条，
  或修复一个已发现的问题。小步快跑，每轮必须留下可验证的成果。

## 每轮流程
1. **读状态**：读 `docs/feature-backlog.md`、`docs/DEVLOG.md` 最近条目、`git log` 最近提交，
   确认上一轮成果与本轮选题；先跑 `go test ./...` 确认基线绿色，基线红了先修基线。
2. **调研（如需要）**：选题涉及外部做法时，查 1–2 个一手来源（官方文档/源码/发布说明），
   把可借鉴点补记到 backlog 对应条目下（只记设计，不复制受 AGPL 等许可污染的代码）。
3. **实现**：最小完整切片——功能代码 + 单元/集成测试 + 必要的管理台/API 面。
   遵守既有约定：纯 Go 标准库优先；密钥只加密存储、绝不回显；审计不落敏感原文；
   数据分级约束高于可用性（如重试不得把数据送往更低密级渠道）。
4. **验证**：`gofmt`、`go vet ./...`、`go test ./...` 全绿；涉及端到端流程时补跑演示模式冒烟。
5. **记录**：更新 backlog 条目状态（doing→done 注明日期）；在 `docs/DEVLOG.md` 追加一条
   （日期、做了什么、关键决策、测试结果、提交哈希）；用户可见变化同步更新 README。
6. **提交与推送（分支 + PR，2026-11-21 Nathan 指示改版：本地完善后再推送，main 只收完整成品；同日再改：整包快照推送优先，把审批次数压到最少）**：
   本地 `git commit`（信息格式 `feat/fix/test/docs(scope): 摘要`）。本地全部开发与验证
   完成并提交之后才允许开始推送；工作区不干净或测试不绿，绝不推送。推送内容只取已提交快照：
   用 `git worktree` 把目标 commit 固定到临时目录后从那里读文件，禁止读正在变动的工作区。
   a. 用 `create_branch` 在远端建本轮分支 `loop/<条目小写>`（如 `loop/f17`），基点为远端 main
      最新提交；若该分支已存在（上一轮中断），复用它续传，不要新开。
   b. 首选整包快照推送（一次审批推全部文件）：严格按 GitHub 连接器的快照推送规程
      （`/opt/hatch/connectors/github/references/snapshot-push.md`）执行——从固定快照目录生成
      NUL 分隔的变更文件清单（放在源目录外），核对分支 head 与各文件同步基点后，用
      `github push-files` 一次把本轮全部变更文件推到该分支，并按规程把成功提交的 SHA 与路径
      写入源目录旁的 `.muse-github-snapshot-sync.json` 同步记录；推送后逐文件用
      `get_file_contents` 读回与本地快照做哈希核对，全部一致才算同步完成。
      仅当 `push-files` 被 GitHub 明确拒绝（如 403）时，才回退到 contents API 逐文件同步
      （`create_or_update_file`，branch 参数填该分支），并在本轮汇报与 DEVLOG 中写明回退原因与
      实测错误；回退时同样要哈希核对齐全。
   c. 同步完成后用 `create_pull_request` 开 PR（base=main，head=该分支），核对 PR 的变更文件
      清单与本轮清单一致后用 `merge_pull_request` 合并；main 只产生一个合并提交，CI 只对
      完整成品跑一次。合并后读回 main 上一两个关键文件验证，并把远端 main 提交号记入 DEVLOG 与本轮汇报。
   d. 若开 PR 或合并失败（冲突、权限等），停下并在本轮汇报中说明，不要回退到逐文件直推 main 的老办法。
   e. 推送失败记录在 DEVLOG 并在下一轮优先处理。**测试不绿绝不推送**。
7. **汇报**：向主对话发一条简短进展（做了什么、测试结果、下一轮计划）。
   失败或阻塞时说明原因与需要的协助；无实质进展不发空汇报。

## 红线
- 不改动项目定位与蓝图已定决策（不绑单一 Agent、分级信任、数据分级路由、AGPL-3.0 许可证（免费使用含商用、修改分发须以 AGPL 开源；非经 Nathan 决定不变更））。
- 不删除既有测试来"让测试通过"；发现 bug 先写复现测试再修。
- 不把任何真实密钥、客户数据写进仓库；演示数据只用虚构的「星河精密」。
- 单轮改动失控（测试反复不过、范围膨胀）时，回滚到本轮开始前的提交状态，
  在 DEVLOG 记明原因，下一轮拆小重试。
- 涉及对外发布、改仓库可见性、删数据等不可逆动作时，停下来等 Nathan 确认——
  Loop 的授权范围是**仓库内开发与推送**，不含对外发布动作。

## 停止条件
- backlog 中 P0/P1 全部 done 且蓝图 MVP 验收场景全过时，Loop 转为维护模式
  （每轮只做巡检 + 小修），并向 Nathan 汇报请求下一阶段目标。
- Nathan 随时可叫停或调整节奏。
